## 3. 这一路遇到的主要问题

### 3.1 UART7 一开始没有输出

#### 现象

- 串口助手最初只能偶尔看到启动信息，或者完全没有稳定日志

#### 排查过程

- 检查了 `UART7` 初始化、时钟、GPIO、句柄导出、中断符号
- 确认代码中已经调用：
  - `MX_UART7_Init()`
  - `Debug_Printf("BOOT OK\r\n")`
- 为了排除 OneNET 和日志封装影响，临时在 `defaultTask` 中直接用：
  - `HAL_UART_Transmit(&huart7, ...)`
  - 每秒发送 `UART7 TEST`

#### 结论

- `UART7` 软件链路本身没有明显问题
- 后续能够稳定看到：
  - `BOOT OK`
  - `UART7 TEST`
  - 网络阶段日志
- 说明 `UART7` 已经可用

### 3.2 `[TCP] INIT FAIL code=1`

#### 含义

- `code=1` 对应 `ESP8266_INIT_STATUS_FAIL_AT`
- 表示发给 ESP 的第一条 `AT` 没有拿到预期 `OK`

#### 可能原因

- `USART6 <-> ESP-01S` 基础串口通信异常
- ESP 供电不稳
- `EN/CH_PD` 没拉高
- ESP 没正常启动
- 波特率不一致

#### 处理

- 重点检查 `USART6` 硬件接线和 ESP 上电状态
- 后续能走到更后面的初始化步骤，说明该问题已基本排除

### 3.3 `[TCP] INIT FAIL code=6`

#### 含义

- `code=6` 对应 `ESP8266_INIT_STATUS_FAIL_CIPMUX`
- 表示 `AT+CIPMUX=0` 失败

#### 直接原因

- ESP 可能残留旧的 TCP 连接状态
- 在已有连接状态下重新执行 `CIPMUX=0`，容易返回 `ERROR`

#### 处理

- 在 `ESP8266_Init()` 中：
  - 保留 `AT+CWJAP?` 查询 WiFi 状态
  - 如果已经连着目标 WiFi，则跳过 `AT+CWJAP`
  - 在 `AT+CIPMUX=0` 前，新增一次尽力清连接：
    - `AT+CIPCLOSE`

#### 结果

- 避免了每次失败都重连 WiFi
- `CIPMUX=0` 阶段的异常明显减少

### 3.4 WiFi 看起来一直重连

#### 现象

- 表面上看像 ESP 一直在掉线重连 WiFi

#### 实际原因

- 代码最初在每次 `Task2` 重试时都会重新执行：
  - `AT+CWJAP="ssid","pwd"`
- 即使 WiFi 还连着，也会被重复发起连接

#### 处理

- 在 `ESP8266_Init()` 中新增：
  - `AT+CWJAP?`
- 如果已经连着目标 WiFi，则直接复用，不再重复 `CWJAP`

#### 结论

- 之前的“WiFi 重连”主要是软件流程导致
- 不是真正的 WiFi 稳定性问题

### 3.5 `[MQTT] CONNECT FAIL code=5`

#### 含义

- 这里的 `code=5` 是本地状态码
- 对应 `ONENET_STATUS_FAIL_CONNECT_ACK`
- 含义是：
  - MQTT CONNECT 已经发出
  - 服务器已经回了 `CONNACK`
  - 但 `CONNACK` 结果不是成功

#### 说明

- 这不是串口错误
- 不是 WiFi 错误
- 不是 TCP 错误
- 而是 OneNET 对 MQTT 登录进行了拒绝

#### 处理

- 给日志增加 `ack` 输出，便于定位 `CONNACK` 真实返回值
- 检查：
  - `clientId`
  - `username`
  - `token`
  - `产品ID / 设备名 / token` 是否为同一套

#### 备注

- 该阶段说明 `TCP` 已经建通，问题已经进入 OneNET 认证层

### 3.6 `[MQTT] SUBSCRIBE FAIL code=9`

#### 含义

- `code=9` 对应 `ONENET_STATUS_FAIL_SUB_ACK`
- 表示订阅请求已发出，但订阅应答没有被判定为成功

#### 最初的实现问题

- 最开始 `OneNet_Subscribe()` 中采用的是：
  - 发完订阅包
  - 立刻等待 `SUBACK`
  - 立刻判断成功或失败
- 这种做法和参考工程不一致

#### 参考工程的做法

- 参考工程 `OneNet_Subscribe()` 只负责发送订阅包
- `SUBACK` 的处理放在 `OneNet_RevPro()` 中
- 主循环统一收包、统一解析

#### 处理

- 将当前工程改成与参考工程一致：
  - `OneNet_Subscribe()` 只发送订阅请求
  - `OneNet_RevPro()` 中处理 `SUBACK`
  - `Task2` 中等待订阅 ready 后再开始发布

#### 结果

- 避免了“刚发完就误判订阅失败”的情况

### 3.7 订阅 topic 体系不一致

#### 最初使用的 topic

- 一开始尝试的是 OneNET 当前 MQTT 文档风格：
  - `dp/post/json`
  - `cmd/request/+`
  - `accepted/rejected`

#### 参考工程使用的 topic

- 参考工程实际使用的是：
  - 发布：`$sys/{pid}/{device}/thing/property/post`
  - 订阅：`$sys/{pid}/{device}/thing/property/set`

#### 最终处理

- 为了完全贴近参考工程，当前工程已改成：
  - 发布：`$sys/S9U9FY9ZdS/Bracelet/thing/property/post`
  - 订阅：`$sys/S9U9FY9ZdS/Bracelet/thing/property/set`

#### 影响

- 上报数据结构也同步改成参考工程风格：

```json
{
  "id": "1",
  "params": {
    "HeartRate": { "value": 78 },
    "BloodOxygen": { "value": 97 }
  }
}
```

## 4. 当前代码中的关键修正

### 4.1 `ESP8266_Init()` 的流程修正

当前流程：

1. `AT`
2. `ATE0`
3. `AT+CWMODE=1`
4. `AT+CWDHCP=1,1`
5. `AT+CWJAP?`
6. 如果未连接目标 WiFi，才执行 `AT+CWJAP`
7. `AT+CIPCLOSE`
8. `AT+CIPMUX=0`
9. `AT+CIPSTART="TCP", host, port`

### 4.2 `Task2` 的流程修正

当前 `Task2` 主要流程：

1. `ESP8266_Init()`
2. `OneNet_DevLink()`
3. `OneNet_Subscribe()`
4. 进入循环：
   - 轮询收包
   - 在 `OneNet_RevPro()` 中等 `SUBACK`
   - 订阅完成后开始周期上报

### 4.3 UART7 日志策略

当前串口7主要用于：

- `BOOT OK`
- `NET TASK START`
- `[TCP] INIT OK / FAIL`
- `[MQTT] CONNECT OK / FAIL`
- `[MQTT] SUBSCRIBE SENT / OK / FAIL`
- `[MQTT] PUBLISH FAIL`
