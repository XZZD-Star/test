# ESP-01S 上云传输背景说明

## 1. 文档目的

这份文档面向“接手本项目云通信部分的另一个 AI / 开发者”，目标是让对方不必重新通读 `ESP8266 / OneNet / MQTT / Task2` 相关源码，也能快速掌握当前项目里 ESP-01S 上云链路的：

- 串口接入方式
- ESP8266 AT 命令封装逻辑
- WiFi + TCP 建链流程
- MQTT 报文组包与解析方式
- OneNet 登录、订阅、发布、下行接收路径
- `Task2` 的状态流、重连逻辑、错误码
- 当前实现里已经完成和还没完成的边界

本文以 **2026-03-28 当前仓库源码** 为准；若和旧排错文档冲突，以源码为准。

## 2. 给 AI 的最小背景摘要

可以先把当前系统记成下面这段“最小配置”：

```yaml
cloud_pipeline:
  transport_module: ESP-01S
  stm32_to_esp_uart: USART6
  debug_uart: UART7
  esp_role:
    - execute AT commands
    - connect WiFi
    - open plain TCP socket
  stm32_role:
    - build MQTT packets locally
    - parse MQTT packets locally
    - manage OneNet session in Task2
  target_cloud:
    host: mqtts.heclouds.com
    port: 1883
    tcp_mode: plain TCP
    tls: false
  mqtt:
    version: 3.1.1
    clean_session: true
    keep_alive_seconds: 60
    subscribe_qos: 0
    publish_qos: 0
    publish_interval_ms: 5000
  onenet_topics:
    publish: "$sys/{product_id}/{device_name}/thing/property/post"
    subscribe: "$sys/{product_id}/{device_name}/thing/property/set"
  current_publish_payload:
    HeartRate: 66
    BloodOxygen: 99
  receive_path:
    esp_uart_rx: single-byte interrupt feed
    esp_buffer: shared 1024-byte buffer
    ipd_parse: "+IPD,<len>:"
  current_limits:
    - no TLS handshake
    - no explicit MQTT ping loop
    - property/set downlink only cached, not applied to business logic
    - publish data still uses fixed test values
```

最重要的一句话是：

> 当前工程不是“ESP 自己跑 MQTT”，而是“ESP-01S 只负责 AT + WiFi + TCP，STM32 自己在本地构造 MQTT 报文、解析 MQTT 回包，再由 `Task2` 管理整条云链路”。

## 3. 核心文件与职责

### 3.1 串口与底层接入

- `Core/Src/main.c`
- `Core/Src/usart.c`

职责：

- 初始化 `USART6`
- 启动 ESP 接收中断
- 把 `USART6` 收到的每个字节喂给 `ESP8266_RxFeedByte()`

### 3.2 ESP8266 传输适配层

- `BSP/ESP8266.h`
- `BSP/ESP8266.c`

职责：

- 管理 ESP 接收缓冲
- AT 命令发送与等待应答
- WiFi / TCP 初始化
- `AT+CIPSEND` 发送数据
- 从 `+IPD` 包中提取下行 TCP payload
- 维护“传输层错误”标志

### 3.3 MQTT 报文层

- `BSP/MqttKit.h`
- `BSP/MqttKit.c`

职责：

- 本地组包：CONNECT / SUBSCRIBE / PUBLISH / PINGREQ
- 本地解包：CONNACK / SUBACK / PUBLISH / PUBACK
- 不依赖 ESP 的 MQTT 能力

### 3.4 OneNet 业务适配层

- `BSP/onenet.h`
- `BSP/onenet.c`

职责：

- 定义 OneNet 连接参数和 topic
- 组 CONNECT / SUBSCRIBE / PUBLISH 报文并经 ESP 发出
- 解析 OneNet 回的 `CONNACK / SUBACK / PUBLISH`
- 保存最近一条下行 `property/set`

### 3.5 网络任务调度层

- `Core/Src/freertos.c`

职责：

- `Task2` 驱动整条上云状态机
- 负责初始化、重连、发布循环、下行处理、日志输出

## 4. 系统中的角色分工

当前项目里 STM32 和 ESP-01S 的职责边界非常明确。

### 4.1 ESP-01S 负责什么

- 执行 AT 命令
- 连接目标 WiFi
- 建立到 OneNet 的 TCP 连接
- 把 STM32 给出的原始 MQTT 字节流发出去
- 把云端回来的 TCP 数据以 `+IPD` 形式回吐给 STM32

### 4.2 STM32 负责什么

- 组织 MQTT CONNECT / SUBSCRIBE / PUBLISH 报文
- 解析 `CONNACK / SUBACK / PUBLISH / PUBACK`
- 管理 OneNet 会话状态
- 管理发布节奏与重连逻辑
- 打印所有云通信日志

所以当前架构本质上是：

> ESP-01S 只是一个“AT 控制的 WiFi-TCP 调制解调器”，不承担 MQTT 协议栈。

## 5. 硬件与串口路径

### 5.1 当前串口分工

- `USART6`
  - STM32 <-> ESP-01S
  - ESP 云通信专用
- `UART7`
  - PC 调试日志输出

### 5.2 `USART6` 的真实接收方式

这一点很重要。

虽然 `CubeMX` 里给 `USART6_RX` 配了 DMA 资源，但 **当前实际运行的 ESP 接收路径不是 DMA 到 IDLE，而是单字节中断接收**：

1. `MX_USART6_UART_Init()` 调 `HAL_UART_Receive_IT(&huart6, &esp8266_rx_byte, 1U)`
2. 每收到 1 字节进入 `HAL_UART_RxCpltCallback()`
3. 调 `ESP8266_RxFeedByte(esp8266_rx_byte)`
4. 再次 `HAL_UART_Receive_IT()` 重新挂下一字节

因此：

- ESP 下行数据是逐字节喂进共享缓冲的
- 不是 DMA 整包搬运
- `hdma_usart6_rx` 当前只是外设配置存在，但主数据通路里没有被真正用于 ESP 收包

### 5.3 调试日志路径

`Task2` 的日志通过 `Debug_Printf()` 输出到 `UART7`，日志前缀主要包括：

- `NET TASK START`
- `[TCP] INIT OK / FAIL`
- `[MQTT] CONNECT OK / FAIL`
- `[MQTT] SUBSCRIBE SENT / OK / FAIL`
- `[MQTT] PUBLISH FAIL`
- `[TCP] TRANSPORT ERROR`
- `[MQTT] SESSION ERROR`

## 6. ESP8266 层的当前实现

## 6.1 关键常量

`ESP8266.c` 当前关键常量：

```c
#define ESP8266_RX_BUFFER_SIZE         1024U
#define ESP8266_CMD_BUFFER_SIZE         160U
#define ESP8266_POLL_DELAY_MS            10U
#define ESP8266_RX_IDLE_MS               20U
#define ESP8266_AT_TIMEOUT_MS          3000U
#define ESP8266_WIFI_TIMEOUT_MS       40000U
#define ESP8266_TCP_TIMEOUT_MS        10000U
#define ESP8266_CIPSEND_TIMEOUT_MS     3000U
#define ESP8266_SEND_TIMEOUT_MS        5000U
```

这些值决定了：

- AT 指令等待超时
- WiFi 入网超时
- TCP 建链超时
- `AT+CIPSEND` 等待 `>` 提示符的超时
- 发送后等 `SEND OK` 的超时

### 6.2 共享接收缓冲

ESP 层内部维护：

- `g_esp8266_rx_buffer[1024]`
- `g_esp8266_rx_count`
- `g_esp8266_rx_last_tick`
- `g_esp8266_transport_error`
- `g_esp8266_last_init_status`

这块缓冲是：

- 中断层持续写入
- 任务层轮询读取
- 没有消息队列
- 也没有按包切分缓存

代码通过短暂关中断的方式读取 `count` / `last_tick` 快照，避免竞争条件。

### 6.3 缓冲溢出行为

如果 `g_esp8266_rx_count >= 1023`：

- 计数会直接回到 `0`
- 新字节从头覆盖

也就是说：

- 一旦缓冲被打满，旧内容会丢失
- 当前实现优先保证“继续接收”，而不是保留历史数据

### 6.4 传输层错误的判定方式

`ESP8266_RxFeedByte()` 会在接收缓冲中实时扫描以下字符串：

- `CLOSED`
- `WIFI DISCONNECT`
- `link is not`
- `CONNECT FAIL`

一旦匹配到任一模式：

- `g_esp8266_transport_error = 1`

这意味着：

- 传输层错误不是靠返回码集中上报
- 而是靠原始串口文本中的关键字触发

### 6.5 `ESP8266_Clear()`

`ESP8266_Clear()` 会：

- 清空接收缓冲
- 把 `rx_count` 清零
- 把 `rx_last_tick` 清零

但不会清 `g_esp8266_transport_error`。

因此通常会和 `ESP8266_ClearTransportError()` 配对使用。

## 7. ESP 初始化流程

`ESP8266_Init()` 是 Task2 进入云链路前的基础准备步骤。

### 7.1 当前初始化顺序

当前真实顺序是：

1. `AT`
2. `ATE0`
3. `AT+CWMODE=1`
4. `AT+CWDHCP=1,1`
5. `AT+CWJAP?`
6. 如果未连接目标 WiFi，则执行 `AT+CWJAP="ssid","pwd"`
7. `AT+CIPCLOSE` 尽力关闭旧 socket
8. `AT+CIPMUX=0`
9. `AT+CIPSTART="TCP","host",port`

### 7.2 WiFi 复用策略

初始化时不是每次都强制重新连 WiFi，而是：

1. 先发 `AT+CWJAP?`
2. 如果当前回复里已经包含目标 `WIFI_SSID`
3. 就跳过 `AT+CWJAP`

所以当前实现是“尽量复用已连接 WiFi”，不是每轮都重新入网。

### 7.3 TCP 连接策略

在设置 `CIPMUX=0` 之前，会先调用 `ESP8266_TryCloseSocket()`：

- 发 `AT+CIPCLOSE`
- 等一小段时间
- 再清缓冲

这是一个“尽力清连接”的保险动作，用来减少残留 socket 状态导致的 `CIPMUX` 失败。

### 7.4 当前错误码

`ESP8266_GetLastInitStatus()` 返回的初始化状态码如下：

| 代码 | 含义 |
| --- | --- |
| `0` | 初始化成功 |
| `1` | `AT` 失败 |
| `2` | `ATE0` 失败 |
| `3` | `CWMODE` 失败 |
| `4` | `CWDHCP` 失败 |
| `5` | `CWJAP` 失败 |
| `6` | `CIPMUX` 失败 |
| `7` | `CIPSTART` 失败 |

`Task2` 会把这些代码打印成：

```text
[TCP] INIT FAIL code=X
```

## 8. 数据发送路径

### 8.1 `AT+CIPSEND` 发送流程

所有 MQTT 报文最终都通过 `ESP8266_SendData()` 发出，流程是：

1. 组 `AT+CIPSEND=<len>`
2. 等待 ESP 返回 `>`
3. 清空接收缓冲
4. 直接发送原始 MQTT 二进制字节流
5. 等待 `SEND OK`

如果任一步失败，就返回 `0`。

### 8.2 当前假设

当前实现默认：

- `CIPMUX=0`
- 只有一个 TCP 连接
- 不处理多连接 ID

因此下行 `+IPD` 解析也按单连接格式处理。

---

## 9. 下行接收路径

### 9.1 `+IPD` 解析方式

`ESP8266_GetIPD(timeout_ms)` 会在共享缓冲里扫描：

```text
+IPD,<len>:
```

解析出 `<len>` 后，如果缓冲中已收到完整 payload，就返回指向 payload 起始位置的指针。

这意味着：

- 函数返回的是 **共享缓冲内部地址**
- 不是新复制出的独立包
- 调用方必须立刻同步处理

### 9.2 当前调用方行为

`Task2` 在主循环里：

1. `ipd_data = ESP8266_GetIPD(50U)`
2. 如果不为空，立刻 `OneNet_RevPro(ipd_data)`
3. 紧接着 `ESP8266_Clear()`

因此：

- 当前设计是“同步处理一包后立刻清空缓冲”
- 下行包不会长期驻留在 ESP 缓冲中

### 9.3 `WaitReceive()` 的实际用途

`ESP8266_WaitReceive()` 的判定逻辑是：

- 缓冲非空
- 并且距离最后一个字节到达已经超过 `20 ms`

当前它主要用于：

- `ESP8266_TryCloseSocket()` 里的“尽力等一等回包”

并不是当前主 MQTT 下行链路的核心函数。

## 10. MQTT 层的当前实现

### 10.1 协议版本与会话参数

`MQTT_PacketConnect()` 当前构造的 CONNECT 报文特征是：

- 协议名：`MQTT`
- 协议级别：`4`
- 即 MQTT 3.1.1
- `clean_session = 1`
- `keep_alive = 60`
- 同时带 `username` 和 `password`
- 当前不带遗嘱消息

### 10.2 当前使用的 packet type

当前代码实际用到了：

- `CONNECT`
- `CONNACK`
- `SUBSCRIBE`
- `SUBACK`
- `PUBLISH`
- `PUBACK`
- `PINGRESP`

其中：

- `PINGREQ` 的组包函数已经实现
- 但当前任务流里 **没有实际调用**

### 10.3 内存分配方式

`MqttKit.c` 当前对 CONNECT / SUBSCRIBE / PUBLISH / PINGREQ 都是：

- 先 `malloc()`
- 组包
- 发送后 `free()`

所以当前 MQTT 报文层是 **动态内存分配模型**，而不是静态预分配。

这是一条很重要的实现事实。

## 12. OneNet 上行路径

### 12.1 CONNECT

`OneNet_DevLink()` 的实际流程：

1. 用 `MQTT_PacketConnect()` 生成 CONNECT 包
2. `ESP8266_SendData()` 发给云端
3. `ESP8266_GetIPD(3000)` 等回包
4. 要求收到的第一包类型必须是 `CONNACK`
5. 再用 `MQTT_UnPacketConnectAck()` 读取返回码

如果 `CONNACK` code 非 0：

- `g_onenet_last_connack_code = connack`
- `g_onenet_session_error = 1`
- `g_onenet_last_status = ONENET_STATUS_FAIL_CONNECT_ACK`

### 12.2 SUBSCRIBE

`OneNet_Subscribe()` 当前只负责：

1. 组一个订阅 `thing/property/set` 的 SUBSCRIBE 包
2. 发送出去

它 **不再同步等待 `SUBACK`**。

真正的 `SUBACK` 处理在：

- `OneNet_RevPro()`

这意味着订阅确认是异步的。

### 12.3 PUBLISH

`OneNet_Publish()` 当前每次组装的 JSON 结构是：

```json
{"id":"<seq>","params":{"HeartRate":{"value":66},"BloodOxygen":{"value":99}}}
```

注意当前事实：

- `HeartRate` 还是固定测试值 `66`
- `BloodOxygen` 还是固定测试值 `99`
- 还没有接入真实传感器数据

这点和旧文档里的 `78/97` 已经不同，必须以当前源码为准。

### 12.4 当前上报属性

当前 OneNet 属性 key 只有两个：

- `HeartRate`
- `BloodOxygen`

并且 payload 使用 `thing/property/post` 风格，不是早期 `dp/post/json` 风格。

## 13. OneNet 下行路径

### 13.1 当前能接收哪些包

`OneNet_RevPro()` 当前处理：

- `CONNACK`
- `SUBACK`
- `PUBACK`
- `PINGRESP`
- `PUBLISH`

### 13.2 `SUBACK` 的作用

收到合法 `SUBACK` 后：

- `g_onenet_last_status = ONENET_STATUS_OK`
- `g_onenet_subscribe_ready = 1`

如果 `SUBACK` 返回失败：

- `g_onenet_session_error = 1`
- `g_onenet_last_status = ONENET_STATUS_FAIL_SUB_ACK`
- `g_onenet_subscribe_ready = 0`

### 13.3 `property/set` 下行的当前落点

收到下行 `PUBLISH` 后：

1. `MQTT_UnPacketPublish()` 解析 topic / payload
2. 如果 topic 精确匹配 `ONENET_TOPIC_PROP_SET`
3. 就调用 `OneNet_CopyDownlink()`

`OneNet_CopyDownlink()` 会把最近一条下行保存到：

- `g_onenet_last_topic[128]`
- `g_onenet_last_payload[256]`
- `g_onenet_downlink_count`

### 13.4 当前下行能力边界

虽然下行包已经可以被解析并缓存，但当前仓库里：

- 没有导出 getter 去读取 `last_topic / last_payload / downlink_count`
- 没有把 `property/set` 继续转换成具体设备动作
- 没有把下行内容接到动作识别模式切换、参数更新或控制逻辑里

所以当前下行链路的真实能力是：

> “能收、能认、能缓存，但还没有真正驱动业务行为”。

## 14. Task2 的实际状态流

`StartTask2()` 是整条云链路的总调度器。

### 14.1 启动阶段

启动后会：

1. `osDelay(1000)`
2. 打印 `NET TASK START`

### 14.2 外层重连循环

每轮开始都会：

1. `ESP8266_Clear()`
2. `ESP8266_ClearTransportError()`
3. `OneNet_ClearSessionError()`
4. `OneNet_ResetSubscribeState()`
5. `subscribe_logged = 0`

然后进入建链阶段。

### 14.3 建链阶段

#### 第一步：ESP / WiFi / TCP 初始化

持续执行：

```c
while (ESP8266_Init() == 0U)
```

失败时每秒重试一次，并打印：

```text
[TCP] INIT FAIL code=...
```

#### 第二步：MQTT CONNECT

持续执行：

```c
while (OneNet_DevLink() == 0U)
```

失败时打印：

```text
[MQTT] CONNECT FAIL code=%u ack=%u
```

如果此时传输层已经坏掉：

- 打印 `[TCP] TRANSPORT ERROR`
- 跳回更外层，重新从 `ESP8266_Init()` 开始

#### 第三步：发 SUBSCRIBE

调用：

```c
OneNet_Subscribe()
```

这里只要求“发送成功”，不是“订阅已确认”。

发送成功后打印：

```text
[MQTT] SUBSCRIBE SENT
```

### 14.4 主循环阶段

进入主循环后，Task2 每轮会做：

1. 检查是否到达 `5000 ms` 发布周期
2. 若到时则调用 `OneNet_Publish()`
3. 调 `ESP8266_GetIPD(50)` 看有没有下行包
4. 若有则 `OneNet_RevPro()` 并清缓冲
5. 如果第一次看到 `subscribe_ready==1`，打印 `[MQTT] SUBSCRIBE OK`
6. 检查 transport error 或 session error
7. 错误则 break，回到外层重连

### 14.5 一个容易忽略的当前行为

当前代码里，发布定时器检查发生在：

- `subscribe_logged` 判断之前

这意味着：

- `SUBACK` 还没确认之前
- 只要已经过了 `ONENET_PUBLISH_INTERVAL_MS`
- `Task2` 仍然可能先执行 `OneNet_Publish()`

所以当前实现 **不是严格意义上的“订阅确认后才开始发布”**，而是：

> “发出订阅请求后立即进入主循环；如果 `SUBACK` 很快到，就先记订阅成功；如果迟迟不到，但 5 秒周期先到了，也可能先发上报。”

这是当前源码行为，不是文档推测。

## 15. 当前错误码体系

### 15.1 ESP 初始化错误码

见第 7.4 节，范围 `0~7`。

### 15.2 OneNet 错误码

`onenet.h` 当前定义：

| 代码 | 含义 |
| --- | --- |
| `0` | OK |
| `1` | CONNECT 组包失败 |
| `2` | CONNECT 发送失败 |
| `3` | 等待 CONNECT 回包失败 |
| `4` | CONNECT 回包类型不是 `CONNACK` |
| `5` | `CONNACK` 返回码非 0 |
| `6` | SUBSCRIBE 组包失败 |
| `7` | SUBSCRIBE 发送失败 |
| `8` | `FAIL_SUB_WAIT`，当前源码路径未使用 |
| `9` | `SUBACK` 失败 |
| `10` | PUBLISH 组包失败 |
| `11` | PUBLISH 发送失败 |
| `12` | 下行 `PUBLISH` 解析失败 |

注意：

- `ONENET_STATUS_FAIL_SUB_WAIT = 8` 目前是历史保留码
- 当前实际执行路径里没有用到它

## 16. 当前实现边界与限制

### 16.1 没有 TLS

虽然 host 写的是 `mqtts.heclouds.com`，但当前建链是：

- `AT+CIPSTART="TCP", ...`

没有：

- SSL/TLS socket
- 证书校验
- MQTT over TLS

### 16.2 没有显式心跳循环

虽然 `MQTT_PacketPing()` 已经实现，也能解析 `PINGRESP`，但当前 `Task2` 没有主动发送 `PINGREQ`。

当前连接之所以大概率能持续，是因为：

- 默认每 5 秒就会有一次 PUBLISH

如果未来发布停止或周期拉长，`keep_alive=60` 可能需要显式心跳逻辑配合。

### 16.3 发布数据不是实时业务数据

当前 `OneNet_Publish()` 使用的是固定测试值：

- `HeartRate = 66`
- `BloodOxygen = 99`

还没有从：

- bio 采样结果
- 动作识别结果
- 真实业务状态

中取值。

### 16.4 下行没有接到业务层

`property/set` 目前只缓存，不执行。

### 16.5 MQTT 内存是动态分配

CONNECT / SUBSCRIBE / PUBLISH 都会 `malloc/free`，长期运行下如果未来包种类增多、频率变高，需要留意堆碎片风险。

### 16.6 ESP 接收缓冲是共享单缓冲

没有分包队列，任何逻辑都必须尽快处理 `+IPD`，否则可能被后续串口数据覆盖。

> 这个 STM32H743 项目的云通信链路使用 ESP-01S，但 ESP 不负责 MQTT 协议，只负责执行 AT 命令、连接 WiFi、建立 TCP；MQTT CONNECT/SUBSCRIBE/PUBLISH 报文都由 STM32 本地 `MqttKit` 组包，OneNet 业务适配由 `onenet.c` 完成，任务调度在 `Task2`。ESP 通信走 `USART6`，实际接收路径是单字节中断 `HAL_UART_Receive_IT -> HAL_UART_RxCpltCallback -> ESP8266_RxFeedByte`，不是 DMA 流式收包。ESP 内部维护一个 1024 字节共享接收缓冲，任务层靠字符串匹配判断 `OK / ERROR / FAIL / CLOSED / +IPD` 等状态。初始化流程是 `AT -> ATE0 -> CWMODE=1 -> CWDHCP=1,1 -> CWJAP? -> 必要时 CWJAP -> CIPCLOSE -> CIPMUX=0 -> CIPSTART(TCP)`。当前云端 host 是 `mqtts.heclouds.com`，端口 `1883`，但实际是明文 `TCP` 而不是 TLS。OneNet 使用 `product_id=S9U9FY9ZdS`、`device_name=Bracelet`，topic 为 `$sys/{pid}/{device}/thing/property/post` 和 `$sys/{pid}/{device}/thing/property/set`。MQTT 使用 3.1.1，`clean_session=1`，`keep_alive=60s`，发布/订阅均为 QoS0。Task2 的外层循环负责初始化和重连；内层循环每 5 秒调用一次 `OneNet_Publish()`，并用 `ESP8266_GetIPD(50)` 轮询下行数据后交给 `OneNet_RevPro()`。当前上报 payload 仍是固定测试值 `HeartRate=66`、`BloodOxygen=99`，不是实时数据。下行 `property/set` 已经可以解析并缓存，但目前还没有接到业务控制逻辑。代码里已经实现 `MQTT_PacketPing()`，但当前任务流没有主动发 `PINGREQ`。另外，当前代码虽有 `subscribe_ready` 标志，但发布定时器并不会严格等待 `SUBACK` 后才开始工作。

## 20. 结论

把当前 ESP-01S 上云部分记成四层最清楚：

1. `usart.c` 负责“把 ESP 串口字节送进系统”
2. `ESP8266.c` 负责“AT / WiFi / TCP / +IPD”
3. `MqttKit.c + onenet.c` 负责“MQTT 报文和 OneNet 业务语义”
4. `freertos.c` 的 `Task2` 负责“会话调度、重连、发布和日志”

只要记住这个分层，再去改 WiFi、改 OneNet 参数、改 MQTT、改发布内容或接入下行控制，定位都会很快。
